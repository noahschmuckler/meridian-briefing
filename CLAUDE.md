# meridian-briefing — Claude Code Context

Standalone editor/publisher for the Optum NY/NJ Provider Briefing. Zero runtime
deps, one JSON document, a public read view at `/`, and a password-gated
in-place editor at `/admin`. Pivot from the shelved
`~/GitHub_Repos/meridian-os/sharepoint-port/` approach.

**Two interchangeable server runtimes, same API + same `state.json` + same `.env`:**
`server.js` (Node `node:http`) is the Linux-dev + orange-device path; `deploy/server.ps1`
(Windows PowerShell 5.1 + .NET Framework `HttpListener`) is the **no-Node production
path** for the CR DEV server (which can't run Node). When you change a route, the
store shape, auth, or the cookie/session contract, **change BOTH servers in lockstep**
— they must stay wire-identical.

**Owner:** Dr. Noah Schmuckler, MD — medical director, Optum NY/NJ. Treat as an
experienced product owner who reads code; name specifics, frame tradeoffs.

## Lifecycle (this is the whole point — mirror the throughline project)

```
Linux dev (here) ── push ──► GitHub ── clone+Sync ──► orange device (test) ── clone ──► CR DEV server (deploy)
  npm run dev                 main                     scheduled task, localhost      SYSTEM task, 0.0.0.0:<port>
  ./data/state.json                                    .\data\state.json              BRIEFING_DB persistent path
```

- Develop + test on Linux, push to `main`.
- Noah clones on the **orange device** (enterprise box) via GitHub Desktop,
  runs `deploy/register-task.ps1`, tests against localhost with a real Node.
- When ready, `git clone` on the **CR DEV server**, run `deploy/install-server.ps1`,
  Billy exposes the port (firewall or IIS reverse-proxy). Update = `git pull` +
  restart the task. `.env` and `data/` are gitignored, so neither pull nor Sync
  touches the password or the editions.

Reference for this lifecycle + the PowerShell idioms: `~/GitHub_Repos/throughline/`
(`server.js`, `deploy/`, `.env.example`). Copy idioms, not features.

## Locked design decisions

- **Zero runtime npm dependencies.** Server is `node:` builtins only. This keeps
  the install story "Node + git, no `npm install`" on Windows boxes (no native
  module compile). **Do not add a runtime dependency** without re-justifying that
  tradeoff — it's the load-bearing constraint behind the whole deploy story.
  `devDependencies` are acceptable; `dependencies` must stay empty.
- **Password hashing is PBKDF2-HMAC-SHA256** (not scrypt/bcrypt/argon2). Chosen
  specifically because it's built into **both** runtimes — Node `crypto.pbkdf2`
  and .NET Framework `Rfc2898DeriveBytes` — so one hash in `.env` verifies on
  either server. (scrypt has no in-box .NET equivalent; bcrypt/argon are native
  modules that'd break zero-deps.) **The params are a cross-runtime contract:
  iterations=600000, key=32 bytes, salt=16 bytes, digest=SHA256, password=UTF-8**
  — they appear in `lib/auth.js`, `deploy/server.ps1`, and both `hash-password.*`
  generators and MUST move together or every login breaks. A known-answer vector
  is pinned in `test/auth.test.mjs` and re-asserted by `server.ps1 -SelfTest`.
  Hash + salt live in `.env` (`ADMIN_PASSWORD_HASH` / `ADMIN_PASSWORD_SALT`),
  generated by `scripts/hash-password.mjs` (Node) or `scripts/hash-password.ps1`
  (Windows/no-Node) — identical output. **The earlier scrypt build's hashes do
  not verify post-swap; regenerate.**
- **The PowerShell server (`deploy/server.ps1`) is a faithful, self-contained
  port — not a thin wrapper.** It reimplements `lib/store.js` + `lib/id.js` +
  `lib/auth.js` in PS. Two landmines are handled and must stay handled: (1)
  **Windows PowerShell 5.1 JSON is unusable for `state.json`** — `ConvertTo-Json`
  defaults to depth 2 and unwraps single-element arrays to bare objects, and
  `ConvertFrom-Json` reads `[{…}]` back as a lone object. So output goes through
  the hand-rolled `Write-BriefingJson` (arrays always render `[…]`) and every
  known-array field is re-wrapped with `To-Array` on read in `Normalize-*`. Don't
  reintroduce `ConvertTo-Json` for the document. (2) **The file is ASCII-only on
  purpose** — 5.1 decodes BOM-less `.ps1` as the ANSI codepage, so the blank-edition
  emoji/middot are built via `[char]::ConvertFromUtf32`, never typed literally.
  Atomic writes use `[System.IO.File]::Replace`; HOST `0.0.0.0`→`+` wildcard prefix
  (needs SYSTEM or a `netsh http add urlacl` reservation, which `install-server.ps1`
  makes). **No PowerShell on the Linux dev box** — verify the PS side with
  `server.ps1 -SelfTest` + the smoke recipe in `deploy/README-server.md` on Windows.
- **Single shared admin password, in-memory sessions.** No per-user accounts in
  v1. Sessions are a `Map` in `lib/auth.js`; a server restart logs everyone out
  (acceptable for a single-admin tool; documented in `.env.example`).
- **One JSON document, atomic writes.** `lib/store.js` owns `state.json`
  (`{schema_version, current_edition_id, editions[]}`); writes go temp-file →
  `rename`. No DB, no per-edition files. `current_edition_id` is always the
  published edition with the latest `published_at`, recomputed on publish/unpublish
  (`recomputeCurrentId`). `normalizeState` self-heals a stale pointer.
- **Frontend: Preact + htm, vendored, no build step.** `public/vendor/` holds
  `preact.module.js`, `hooks.module.js`, `htm.module.js`; `public/index.html`
  wires them via an import map. Chosen over a CDN import map so the deploy is
  offline-capable on the enterprise network. Re-vendor by curling the same
  unpkg URLs if you bump versions.
- **One renderer, two modes.** `public/briefing.js`'s `<Briefing>` component
  renders both the provider view and the editor; the only difference is whether
  an `edit` prop (with `onEdit`/`addItem`/`removeItem`/`moveItem`) is passed.
  Read mode = `null`. Keep it that way — don't fork a separate editor renderer.
- **Edits autosave (debounced PATCH).** Editor edits update a working copy and
  schedule a 500ms-debounced `PATCH`; the top bar shows Saving/Saved/Failed.
  No optimistic illusions — the indicator reflects the server response.
- **Visual language is the meridian-os Briefing.** DM Sans + DM Serif Display,
  `--crh-*` palette, parchment background, color-tinted brief-cards, navy panel
  header. `public/briefing.css` is lifted from
  `meridian-os/src/apps/briefing/briefing.css` (kept under a `.briefing-app`
  scope) + an `.admin-mode` block for edit affordances. The meridian-os Briefing
  app stays the design canvas; promote new card types/layouts here deliberately.
  **No runtime coupling** between the two apps.
- **Server speaks plain HTTP.** TLS + friendly hostname are Billy's layer (IIS
  reverse-proxy or a firewall'd port). `HOST=0.0.0.0` to expose directly;
  `127.0.0.1` when IIS fronts it. Port is `.env`-driven.

## File map

```
server.js            node:http server; routes (public read / admin CRUD / static SPA); auth guard
lib/
  store.js           state.json I/O (atomic), normalize, blankEdition, recomputeCurrentId, currentEdition
  auth.js            scrypt hash/verify, in-memory session store, cookie helpers
  id.js              newEditionId (ed_<YYYYMMDD>_<rand4>), newSessionId (32-byte hex)
public/
  index.html         SPA shell; import map → vendored Preact/htm; mounts briefing.js
  briefing.js        Preact app: ReadApp / AdminApp(Login+Editor) / shared <Briefing> renderer
  briefing.css       lifted briefing styles (.briefing-app scope) + .admin-mode edit affordances
  favicon.svg        navy/teal/gold mark
  vendor/            preact.module.js, hooks.module.js, htm.module.js (no build step)
scripts/
  seed.mjs           writes one published edition (current TSX content) to state.json — DEV ONLY
  hash-password.mjs  prompt → PBKDF2 → prints ADMIN_PASSWORD_HASH + SALT lines for .env (Node)
  hash-password.ps1  same, in PowerShell, for Windows/no-Node boxes (identical PBKDF2 output)
test/
  store.test.mjs     atomic roundtrip, normalize, recompute current
  auth.test.mjs       scrypt verify, cookie parse/build, session create/validate/expire/slide
  api.test.mjs        end-to-end over HTTP: login → draft → patch → publish → public GET → delete
deploy/
  server.ps1         no-Node production server: PowerShell/.NET HttpListener port of server.js
                     (reimplements store/id/auth; hand-rolled JSON serializer; -SelfTest flag)
  register-task.ps1  orange-device logon scheduled task (BriefingServer), in place
  install-server.ps1 CR DEV server startup task as SYSTEM; launches server.ps1; reserves URL ACL
  bundle.sh          Linux zip-bundle fallback (no-git boxes)
  README-orange.md   orange test rung
  README-server.md   CR DEV deploy rung — PowerShell-primary (+ smoke recipe, Node/nssm/IIS notes)
.env.example         PORT/HOST/BRIEFING_DB/ADMIN_PASSWORD_*/SESSION_TTL_DAYS
```

`.env` and `data/` are gitignored. There are no runtime deps, so no
`node_modules` in deploys.

## Conventions

- **Run/verify locally before pushing:** `npm test` (all green) + a curl smoke
  of the 3 public + the admin lifecycle. There's no CI on the repo (yet).
- **Git:** GitHub Flow off `main`. No branch protection set initially. End commit
  messages with the Claude co-author trailer.
- **Schema changes** bump `SCHEMA_VERSION` in `lib/store.js` and teach
  `normalizeState`/`normalizeEdition` to migrate older docs on read (the store
  already normalizes every read, so additive fields are free).
- **Don't edit `meridian-os`** from this repo's work — it's a sibling reference,
  not a dependency.
